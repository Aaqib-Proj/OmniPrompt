# Deploying OmniPrompt to Hostinger

Two separate things live on Hostinger:

| Piece | Where | How it gets there |
|---|---|---|
| Frontend (React build) | the website's `public_html` | upload `frontend-dist.zip`, extract at the root |
| Backend (Express + Prisma) | the `api.syncnomy.com` Node.js app | upload `backend-deploy.zip`, then press **Build** |
| Database | Hostinger MySQL | already created; the backend reaches it via `DATABASE_URL` |

## Build the archives

```bash
cd backend && npm run build && cd ../frontend && npm run build && cd .. && node scripts/package-deploy.mjs
```

That produces `backend-deploy.zip` and `frontend-dist.zip` in the repo root.

## Frontend

1. hPanel → the site → **File Manager** → `public_html`.
2. Upload `frontend-dist.zip` and extract it there. The contents go at the root, not in a subfolder.
3. Confirm `.htaccess` landed. It is generated at build time and is not optional:
   - without its rewrite rule every deep link (`/explore`, `/prompts/:slug`) returns 404,
   - it carries the Content-Security-Policy, HSTS and cache headers.
4. Load the site and check the browser console is clean.

`.htaccess` is regenerated by `frontend/scripts/postbuild-htaccess.mjs` on every build, because the
CSP contains a hash of the inline theme script in `index.html`. Editing it by hand on the server will
be overwritten on the next extract — change the generator instead.

## Backend

1. hPanel → `api.syncnomy.com` → **Node.js** app.
2. Upload `backend-deploy.zip` to the app directory and extract.
3. Press **Build**. Hostinger only runs the script literally named `build`, which the packaging
   script rewrites to `prisma generate && prisma db push`.
4. `GET https://api.syncnomy.com/api/health` should return `{"status":"ok","service":"OmniPrompt API",...}`.
   If it still says `PromptIt API`, the old deployment is still running.

### Loading the signature prompt library

`backend/prisma/import-signature-prompts.ts` adds 30 curated prompts across all seven
categories. It is deduplicated by slug, so re-running it updates rather than duplicates.

Locally:

```bash
cd backend && npm run import:signature
```

On Hostinger there is no shell, so run it as part of one build. Edit the deployed
`package.json` build script for a single deploy:

```json
"build": "prisma generate && prisma db push && node prisma/import-signature-prompts.js"
```

Build once, confirm the prompts appear, then put the script back to
`prisma generate && prisma db push` so later deploys don't re-run the import.

The compiled `.js` ships alongside the `.ts` on purpose: `tsx` is a devDependency and
the host does not install it, so the import has to run under plain `node`.

### Repairing broken cover images

`backend/prisma/repair-broken-media.ts` checks every media URL on every prompt and
fixes the dead ones. It is a dry run unless you pass `--apply`.

```bash
cd backend && npm run media:check     # report only
cd backend && npm run media:repair    # replace dead covers
```

Dead covers are **replaced** with a verified stock image from a per-category pool,
chosen deterministically from the prompt slug, and the row's `mediaType` is corrected
to `IMAGE` (a dead audio file becomes a still, not a broken player). Pass
`--remove` after `--apply` to delete the rows instead — but note that on the
production database 32 of 42 prompts had *every* media row dead, so removal leaves
most of the grid blank.

Set `MEDIA_DIR` before running with `--apply`. The script refuses to run if rows
point at a media directory that doesn't exist, because that would replace genuine
uploads with stand-ins.

On Hostinger, run it the same way as the prompt import — as one build:

```json
"build": "prisma generate && prisma db push && node prisma/repair-broken-media.js --apply"
```

### Things that will bite you

- **A successful build consumes the uploaded zip.** Every deploy needs a fresh upload.
- **A failed build wipes the deployment and the environment variables.** Re-enter them, then build again.
- **Changing an environment variable needs a rebuild**, not a restart. Restart alone is a no-op.
- **`prisma/schema.prisma` must be the MySQL one.** The packaging script copies `schema.mysql.prisma`
  over it. Shipping the SQLite schema makes Prisma hang at connect time rather than fail loudly.
- **Never delete `.htaccess`** in either location.
- `dist/` is compiled locally and shipped prebuilt — the host does not install the
  devDependencies that `tsc` needs.

## Environment variables (backend)

| Name | Notes |
|---|---|
| `DATABASE_URL` | `mysql://user:pass@host:3306/dbname` |
| `JWT_SECRET`, `JWT_REFRESH_SECRET` | long random strings; the server refuses to start without them |
| `NODE_ENV` | `production` — also what disables the dev Google sign-in path |
| `CORS_ORIGIN` | comma-separated allowlist of frontend origins |
| `GOOGLE_CLIENT_ID` | |
| `MEDIA_DIR` | absolute path **outside** `public_html` so redeploys don't wipe uploads |
| `HIGGSFIELD_API_KEY` | optional; only signed-in users can spend it |

## Frontend environment (`frontend/.env.production`)

| Name | Notes |
|---|---|
| `VITE_API_URL` | backend origin; also drives the CSP `connect-src` |
| `VITE_SITE_URL` | public site URL, used for link-preview tags — update when the real domain lands |
| `VITE_GOOGLE_CLIENT_ID` | |
